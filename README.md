# План переделки BecqMoni под Linux (без «лишних» библиотек Microsoft)

Репозиторий: https://github.com/Am6er/BecqMoni — локальная копия: `./BecqMoni`
Лицензия: GPL-2.0 (обязательна к сохранению при распространении производной работы).

---

## 1. Что это за продукт (по факту кода)

BecqMoni / BecquerelMonitor — настольное приложение для гамма-спектрометрии:

- **Приобретение спектров** с приборов разных производителей;
- **Обработка**: энергетическая/фШПВ калибровка, поиск пиков, определение нуклидов, дозиметрия;
- **Full Spectrum Analysis (FSA)** — разложение спектра по библиотеке нуклидов (каскадные совпадения, матрица отклика);
- **EfficiencyMaker** — расчёт эффективности детектора, материальные/сечения базы, электронный транспорт, геометрия, опционально GPU (CUDA);
- **NuclideBase** (`nucdb.sqlite`), материалы/перенос (`matdb.sqlite`), схемы Geant4 (`schemedb.sqlite`);
- **Импорт/экспорт** (N42, XML-спектры), отчёты, конфиги приборов, локализация ru/en.

### Текущий технологический стек

| Слой | Технология | Статус на Linux |
|---|---|---|
| Рантайм | .NET Framework **4.8** (`TargetFrameworkVersion=v4.8`) | ❌ только Windows |
| Сборка | MSBuild, старый `.csproj` (ToolsVersion 12), `packages/`, `.suo` | ❌ |
| UI | **WinForms** + скриншоты в `.resx`, ~496 `.cs` | ❌ (WinForms в .NET является Windows-only) |
| Докинг | `DockPanelSuite` / `DockPanelSuite.ThemeVS2015` 3.1.1 | ❌ WinForms-зависим |
| Таблицы | собственный форк **XPTable** + Win32 P/Invoke | ❌ |
| Графики | кастомные WinForms-контролы (`EnergySpectrumView` и др.) | ❌ |
| Аудио (звуковая карта как детектор) | **WinMM** (`waveIn/waveOut`), **CoreAudioApi** (`winmm.dll`, COM) | ❌ |
| USB HID (Amplituda USB) | `hid.dll`, `setupapi.dll`, `kernel32.dll` (`HidNative.cs`) | ❌ |
| Bluetooth (RadiaCode/Obsidian) | `InTheHand.Net.Bluetooth`, `InTheHand.BluetoothLE` | ⚠️ частично, привязка к стеку Windows |
| Serial / TCP (AtomSpectra, Amplituda Serial) | `System.IO.Ports` 7.0, `Socket` | ✅ кросс-платформенно |
| GPU-матрица | `rmgpu_f.dll` + `nvcuda.dll` через `kernel32` `LoadLibrary` | ❌ |
| Парсинг спектров | **нативная `SpecUtilsNet.dll`** (Windows x64, из SpecUtils) + `kernel32!GetShortPathNameW` | ❌ (нужен `.so` или чистый C#) |
| БД | `Microsoft.Data.Sqlite` 6.0.9 + `SQLitePCLRaw.*` (бандл e_sqlite3) | ✅ (есть linux-нативы) |
| Численные методы | `MathNet.Numerics` 5.0 | ✅ (MIT, кросс-платформенно) |
| Обновления | **ClickOnce** (`System.Deployment`, `PublishUrl`, `InstallUrl`) | ❌ |
| Конфиг/пути | `%AppData%\BecqMoni`, реестр (`FsaAnalyzer.cs`), `Environment.CurrentDirectory` | ❌ |
| Сборка/тесты/инструменты | 100+ PowerShell `.ps1` + Python `.py` | ⚠️ PS только под Windows |

### Важное позитивное наблюдение

В коде уже есть **абстракция безоконного режима**: класс `AppUi`
(`BecquerelMonitor/GlobalConfigManager.cs:38`) с `HasWindows` / `Report` /
`AskYesNo`, а также сторож `tools/check_headless.py`, который требует, чтобы
безоконный путь не звал `MessageBox.Show`. Это значит: **расчётное ядро уже
частично отделено от окон** — на этом и надо строить порт.

## 2. Стратегия: три варианта

| Вариант | Суть | Оценка |
|---|---|---|
| **A. Wine / Mono** | Запустить exe под Wine или собрать под Mono | ❌ нарушает требование «без лишних библиотек Microsoft»; WinForms/ClickOnce/нативы под Wine хрупки; не решение, а отсрочка |
| **B. Avalonia UI + отдельное ядро** | Ядро вынести в кросс-платформенную библиотеку, UI переписать на Avalonia | ✅ **рекомендуется**: действительно Linux-нативно, сохраняет научный код |
| **C. Headless CLI + минимальный GUI** | Сначала CLI-ядро (анализ/конвертация), GUI позже | ✅ как **первый этап** работы B — даёт результат рано |

**Рекомендация: B через C.** Сначала ядро как CLI (быстрый рабочий результат
на Linux), затем UI на Avalonia.

Целевой стек:
- Рантайм: **.NET 8** (LTS), кросс-платформенный.
- UI: **Avalonia UI 11** + `Dock.Avalonia` (докинг) + `Avalonia.Controls.DataGrid`.
- БД: `SQLitePCLRaw.provider.dynamic_cdecl` → системная `libsqlite3.so`, либо `sqlite-net` (**уходим от `Microsoft.Data.Sqlite`**).
- Численные: `MathNet.Numerics` (оставляем).
- Serial: `System.IO.Ports` (оставляем).
- TCP: `System.Net.Sockets` (оставляем).
- HID: `HidSharp` / прямой `hidraw`/`libusb`.
- Bluetooth: BlueZ через D-Bus (`Tmds.DBus`) вместо `InTheHand`.
- Аудио: ALSA/PulseAudio через `SDL2`/`OpenAL`/`NAudio` вместо WinMM/CoreAudioApi.
- Обновления: собственный апдейтер + пакеты `AppImage` / `.deb` / Flatpak (без ClickOnce).
- Конфиг/пути: `XDG_CONFIG_HOME` (`~/.config/BecqMoni`), без реестра.
- Нативы: `SpecUtils` собрать как `libSpecUtilsNet.so` **или** заменить чистым C#-парсером (см. §4, пакет WP-3 — критично).

## 3. Целевая архитектура

```
RadiationSoft/
├─ BecqMoni/                     # исходный репозиторий (эталон, не трогаем логику без нужды)
└─ becqmoni-linux/               # новый solution
   ├─ BecqMoni.Core/             # net8.0, БЕЗ WinForms/System.Windows.Forms
   │   ├─ Spectra/               # EnergySpectrum, разбор, N42, калибровки
   │   ├─ PeakDetector/          # FWHMPeakDetector (уже почти чистый C#)
   │   ├─ FullSpectrumAnalysis/  # FSA
   │   ├─ EfficiencyMaker/       # расчёт эффективности (кроме GPU)
   │   ├─ Nuclide/               # NuclideBase, LineLibrary
   │   ├─ Storage/               # SQLite-доступ (кросс-платформенно)
   │   ├─ Devices/               # абстракции приборов + транспорты
   │   └─ Config/                # сериализация конфигов, XDG-пути
   ├─ BecqMoni.Acquisition/      # драйверы: Serial, TCP, HID, BLE, Audio (Linux)
   ├─ BecqMoni.Cli/              # net8.0 headless: анализ/конвертация/расчёты
   ├─ BecqMoni.Desktop/          # Avalonia UI (порт MainForm + окна/панели)
   ├─ BecqMoni.Tests/            # xUnit; перенос python-проверок
   └─ packaging/                 # AppImage/deb/flatpak, .desktop, иконки
```

Правило: **`BecqMoni.Core` не должен ссылаться на `System.Windows.Forms`,
`System.Drawing`, `Microsoft.Win32.*`, `kernel32` и т.п.** — это критерий
готовности ядра.

## 4. Пакеты работ (work packages)

### WP-1. Инвентаризация и сборка эталона
- Зафиксировать версию (сейчас `ApplicationVersion=2026.10.28.02`), ветку `master`.
- Проверить, что текущий код **собирается** (на Windows/Wine-сборочном агенте или через `dotnet build` после WP-2), чтобы иметь baseline для диффов.
- Составить точную карту: какие `.cs` зависят от WinForms / P/Invoke / реестра / ClickOnce (скрипт-анализатор по `using` и `DllImport`).
- **Артефакт:** отчёт «файл → Windows-зависимости».

### WP-2. Каркас solution на .NET 8
- SDK-style `.csproj`, `Directory.Build.props`, `nuget.config` без `packages/`.
- Подключить `MathNet.Numerics`, `System.IO.Ports`, выбранный SQLite-провайдер.
- CI: GitHub Actions `ubuntu-latest`, `dotnet build` + `dotnet test`.
- **Артефакт:** пустой, но собирающийся на Linux solution.

### WP-3. Замена нативного парсера спектров (КРИТИЧНО)
Текущий `BecquerelMonitor/SpecUtilsNative.cs` грузит `SpecUtilsNet.dll` (Windows
x64) и использует `kernel32!GetShortPathNameW`. Варианты:
1. **Собрать `libSpecUtilsNet.so`** из https://github.com/Am6er/SpecUtilsCS /
   SandiaLabs/SpecUtils с C-обёрткой (тот же ABI, `[DllImport]` без `kernel32`).
2. **Чистый C#-парсер** форматов (нужно определить, какие форматы реально
   читаются — N42/CHN/SPE и т.п.) — убирает нативную зависимость целиком.
- Убрать `GetShortPathNameW` (Linux-пути и так UTF-8).
- **Артефакт:** чтение тех же тестовых спектров на Linux, сверка чисел с Windows-эталоном.

### WP-4. Ядро без UI
- Вынести `EnergySpectrum`, `N42/*`, `FWHMPeakDetector/*`, `FullSpectrumAnalysis/*`,
  `Nuclide*`, `Calibration*`, `Utils/*` в `BecqMoni.Core` (net8.0).
- Убрать вызовы `MessageBox` из ядра — заменить на `AppUi`-подобную абстракцию
  (интерфейс `IUserInteraction`), реализуемую в UI и в CLI.
- **Артефакт:** `BecqMoni.Core.dll` собирается и тестируется на Linux без WinForms.

### WP-5. Хранилище (SQLite) без Microsoft-пакетов
- Файлы БД (`nucdb.sqlite`, `matdb.sqlite`, `schemedb.sqlite`) — формат тот же,
  читаются кросс-платформенно.
- Заменить `Microsoft.Data.Sqlite` + `SQLitePCLRaw.bundle_e_sqlite3` на системную
  `libsqlite3` через `SQLitePCLRaw.provider.dynamic_cdecl` (или `sqlite-net`).
- Сохранить режим read-only (`file:…?mode=ro&uri=true`) как в README репозитория.
- **Артефакт:** доступ к трём базам на Linux, сверка запросов.

### WP-6. Конфигурация и пути (XDG)
- `%AppData%\BecqMoni` → `$XDG_CONFIG_HOME/BecqMoni` (по умолчанию `~/.config/BecqMoni`).
- Данные/кэш → `$XDG_DATA_HOME` / `$XDG_CACHE_HOME`.
- Убрать чтение реестра (`FsaAnalyzer.cs`).
- Убрать привязку к `Environment.CurrentDirectory` как к каталогу программы.
- Совместимость: уметь читать старые XML-конфиги (`config/BecquerelMonitor.xml`,
  `config/device/*.xml`, `config/layout/*.xml`) без изменений.
- **Артефакт:** загрузка существующих конфигов на Linux.

### WP-7. Транспорты приборов (кросс-платформенные)
| Прибор | Сейчас | Порт |
|---|---|---|
| AtomSpectra VCP/Serial | `System.IO.Ports` | оставить; проверка `/dev/ttyUSB*`, права (udev) |
| AtomSpectra TCP/REST | `Socket` | оставить как есть |
| Amplituda Serial | `System.IO.Ports` | оставить |
| Amplituda USB | `hid.dll`/`setupapi` (`HidNative.cs`) | `HidSharp` или `hidraw`/`libusb`; правила udev |
| RadiaCode / Obsidian | `InTheHand` Bluetooth | BlueZ через D-Bus (`Tmds.DBus`), BLE GATT |
| Audio-спектрометр | WinMM + CoreAudioApi | ALSA/PulseAudio (`SDL2`/`OpenAL`/`NAudio`), Enumerate capture devices |
| Термометры (USB/встроенные) | нативы/WMI | пересмотреть под Linux |

- Определиться, какие приборы **обязательны** для первой версии (предлагаю:
  Serial/TCP первыми — они уже кросс-платформенны).
- **Артефакт:** таблица «прибор → статус на Linux» + рабочие драйверы приоритетных.

### WP-8. UI на Avalonia (основной объём)
- Порт `Program.cs` → `BecqMoni.Desktop/Program.cs` (единый экземпляр через
  файловую блокировку/`flock`, без `Mutex`-имени с путём exe).
- Порт окон/панелей: `MainForm`, `DocEnergySpectrum`, панели `DC*View`,
  `FSAReportView`, `EfficiencyMakerForm`, `*DeviceForm*`, диалоги настроек.
- `DockPanelSuite` → `Dock.Avalonia`.
- `XPTable` → `Avalonia.Controls.DataGrid` (проверить редакторы ячеек/рендереры).
- Кастомные графики (`EnergySpectrumView`, `PulseView`, калибровочные графики) →
  отрисовка на `Avalonia.Controls` (рисуем вручную через `DrawingContext`, как
  сейчас в WinForms, либо через `ScottPlot`/`LiveCharts`).
- Скриншоты `.resx` → Avalonia `.axaml` (перенос вручную, автоматизация ограничена).
- Локализация ru/en сохраняется (`.resx`/`CultureInfo`).
- **Артефакт:** запуск и базовый сценарий (открыть спектр → разбор → экспорт) на Linux.

### WP-9. GPU-матрица отклика (опционально)
- `rmgpu_f.dll` + `nvcuda.dll` через `kernel32` → на Linux: `librmgpu.so` +
  `libcuda.so` через `dlopen` (`DllImport("libdl")`/`NativeLibrary.Load`).
- Либо явно сделать функцию **опциональной** (CPU-путь обязателен, GPU — если есть).
- **Артефакт:** CPU-путь работает всегда; GPU — при сборке под CUDA.

### WP-10. Упаковка и обновления
- Убрать ClickOnce (`System.Deployment`, `PublishUrl`, `InstallUrl`, `app.manifest`,
  сертификат `ManifestCertificateThumbprint`, `.suo`).
- Собственный апдейтер (проверка версии по HTTP, скачивание пакета) или отдать
  обновления менеджеру пакетов.
- Сборка: `dotnet publish -r linux-x64`, затем `AppImage`/`.deb`/Flatpak,
  `.desktop`-файл, иконки, правила udev для USB/BLE.
- **Артефакт:** устанавливаемый пакет, запускается двойным кликом/из меню.

### WP-11. Тесты и инструменты
- Перенести python-проверки `tools/check_*.py` (они языко-нейтральны) — оставить.
- PowerShell-сборщики (`build_all.ps1`, `mk_appwd.ps1`) заменить Makefile/`dotnet`
  + bash-скриптами.
- Сохранить «безоконный» сторож (`check_headless.py`) и требование к `IUserInteraction`.
- Добавить сверку чисел Windows↔Linux на одних входных спектрах (регресс).
- **Артефакт:** `dotnet test` + портированный набор проверок зелёные на Linux.

## 6. Риски и решения

| Риск | Влияние | Смягчение |
|---|---|---|
| Нативная `SpecUtilsNet.dll` без исходников/Linux-сборки | Критично (чтение спектров) | Собрать `.so` из SpecUtilsCS; иначе чистый C#-парсер (WP-3, делать первым) |
| UI-переписывание ~500 файлов WinForms | Максимальный объём | Начать с headless CLI (M1), UI — поэтапно; не тащить XPTable/DockPanel, взять готовые Avalonia-компоненты |
| Зашитая логика Windows в расчётах (пути, реестр, `MessageBox`) | Средне | Вынести в `Core` + `IUserInteraction`, ловить анализатором |
| Различия чисел из-за округления/натив-парсера | Средне | Регресс-сверка Windows↔Linux на одних входах |
| Bluetooth/HID вендор-специфичны | Средне | BlueZ/hidraw — стандартные API; проверить на реальных приборах |
| Объём PowerShell-тулинга | Низко-средне | Переносить по мере надобности, python уже нейтрален |
| GPL-2.0 | Юридически | Сохранять лицензию и уведомления при распространении |

## 7. Что нужно уточнить у владельца продукта

## 8. Рекомендуемый первый шаг

Начать с **M1 (headless ядро)**: он даёт работающий на Linux продукт без UI,
проверяет самые рискованные узлы (нативы, базы, конфиги) и не блокируется

### Драйверы сроков

- **~50–60 % всей работы — WP-8 (UI).** WinForms→Avalonia — почти ручной перенос
  десятков форм, кастомных графиков и `.resx`-скриншотов; автоматизация ограничена.
- **WP-3 (натив из исходников) — отдельный риск:** 2–5 pw, но может выйти за
  рамки, если у `SpecUtils`/`SpecUtilsCS` нет готовой CMake-сборки под Linux или
  если формат спектров завязан на Windows-специфику. Это **первое, что надо
  проверить прототипом**, до оценки остального порта.
- **Linux `.NET 8`** даёт кросс-платформенные serial/TCP/SQLite и убирает
  ClickOnce/реестр — это экономит недели против варианта Mono/Wine, но **никогда
  не работает для WinForms** — UI так или иначе переписывается.
- Параллелизация почти линейна только на старте (M1); к M3–M4 (UI + приборы)
  появляется интеграционный оверхед, поэтому выигрыш от 3+ человек невелик.

### Минимальный полезный релиз (быстрый результат)

**Headless-CLI, читающий те же спектры и считающий то же на Linux** — **1.5–2.5
месяца** силами одного разработчика. Это рекомендуемый первый контрактный этап:
он снимает главный технический риск (натив-парсер) и уже даёт ценность без UI.

## 10. Оценка в режиме агентской разработки (AI-агент, этот инструмент)

Оценка ниже — пессимистично-реалистичная и **не выдаёт скорость письма за
скорость сдачи**. Агент быстро пишет код, но срок теперь упирается не в
написание, а в **проверку** и **доступ к железу/эталону Windows**.

### Что ускоряется и во сколько

| Тип работы | Ускорение против человека | Почему |
|---|---|---|
| Чистый C#: вынос ядра, замена SQLite, конфиги, транспорты (код), скрипты сборки | **×3…×5** | механическая, проверяемая компилятором |
| Генерация UI Avalonia (XAML + код) | **×2…×3** | пишется быстро, но КАЖДОЕ окно надо визуально проверить |
| Сборка `libSpecUtilsNet.so` из исходников, ABI, сверка | **×1.5…×2** | C++/CMake, ошибки ловятся только итеративной сборкой |
| Тесты, регресс Windows↔Linux | **×1…×1.5** | нужен эталонный Windows-прогон, которого у агента нет |
| **Железо в контуре: реальные приборы, BLE, USB-HID, аудио, GPU** | **×1 (НЕ ускоряется)** | агент не может подключить физический прибор — гейт на человеке |
| **Визуальная/UX-приёмка GUI** | **×1…×1.5** | нужны глаза человека и скриншоты |

### Что агент физически не может закрыть сам

- Подключить и проверить настоящие спектрометры (AtomSpectra, RadiaCode, Obsidian, Amplituda).
- Услышать/увидеть аудио-спектрометр, проверить BLE-спаривание и udev-права на живом железе.
- Собрать и прогнать CUDA-путь на реальной NVIDIA-карте.
- Сверить числа с **Windows-эталоном** (нужна Windows-машина или её прогон).
- Оценить «похожесть» интерфейса на оригинал глазами.

Всё это — **гейты на человеке**; код к ним можно написать заранее, но приёмка ждёт вас.

### Оценка по фазам (активное время агента / календарь)

| Этап | Активная работа агента | Календарь (с ревью и сборками) |
|---|---|---|
| M1 — headless-CLI ядро (WP-1…6) | **2–4 дня** | 4–8 дней |
| WP-3 — натив `.so` (риск-спайк) | 3–6 дней | 4–12 дней |
| WP-8 — UI Avalonia | 1.5–3 нед | 3–6 нед (визуальная приёмка) |
| WP-7 — транспорты (код) | 3–7 дней | гейт железа: **+1–3 нед ожидания** |
| WP-9 GPU (опция) | 3–5 дней | гейт железа |
| WP-10/11 — упаковка, тесты | 4–7 дней | 1–2 нед |

### Итоги для агента

| Объём | Один агент, последовательно | Agent Manager, 3–4 параллельных сессии (ядро ‖ UI ‖ приборы ‖ упаковка) |
|---|---|---|
| M1 — headless-CLI | **3–6 дней** | **2–4 дня** |
| Полный продукт, Serial/TCP, GUI | **4–7 нед** | **2.5–4 нед** |
| Полный продукт, все приборы + GPU | **6–11 нед** | **3.5–6 нед** *(+ гейты железа)* |

Буфер на непознанное (**+30…50 %**, натив-парсер и специфика приборов) уже частично
в таблице; при плохой сборке `SpecUtils` под Linux верхняя граница уходит к
**8–12 неделям** даже в параллельном режиме.

### Вывод

Агентская разработка сжимает сроки примерно **в 2.5–4 раза** на коде (полный
продукт: ~**3–6 недель** календаря с параллельными сессиями против 6–9 месяцев у
команды из двух человек) **при трёх обязательных условиях**:

1. **есть железо** (приборы, NVIDIA, аудио) и кто-то, кто его подключит и примет;
2. **есть Windows-эталон** для сверки чисел;
3. **человек быстро отвечает** на ревью/вопросы (иначе агент стоит в ожидании — а
   это и есть узкое место, а не скорость написания кода).

Без этих условий агент доведёт до «собирается и считает на Linux» за
**3–6 недель**, но «принято на реальных приборах» закроет только вместе с вами.
